<h2>编译器</h2>


**结构化表示、分析、变换**

编译器 = 词法分析 + 语法分析 + 语义分析 + 编译优化 + 代码生成？

Compiler是编程语言实现，从应用上来说，摩尔定律结束后，越来越多的新硬件设计出现，需要编译器的支持。除了硬件需求，在软件上的新抽象、新需求也对编译器开发有着要求。

Compiler不只是编程语言实现，LLM和Compiler都是处理字符串，不同的是LLM处理的是非结构化的字符串，优势是“涌现”了思考与推理能力，劣势是会产生幻觉，不可执行，不客观。我认为Compiler对语言的结构化表示、分析与变换在LLM时代有着关键性作用。

**编译器的类型**

语言类型：静态语言、动态语言
编译器类型：编译器、解释器
这两者可以自由组合，静态语言不意味着必然采用编译器

执行策略：
1. AOT：Source -> Native Code
2. Interpreter：Source -> Bytecode -> VM
3. JIT：Source -> Bytecode / IR -> Native Code

**编译器、解释器背后的性能与灵活性的trade off**

根据编程语言的应用场景可以总结一个规律，那就是功能越固定，越靠近底层的应用场景下，都更倾向于编译器，一次编译后续高效运行；功能变化越大，应用场景越贴近用户，越灵活的时候，都更倾向于使用解释器，对一个小的部分进行修改不需要重新编译整个项目，随时修改随时部署上线，例如Youtube早期后端大量使用python进行开发，随着规模增长他们将性能敏感的模块迁移到了Go和C++。

这里我们可以看到一个trade off，也就是整体项目的运行效率和项目调整的灵活性之间的一个取舍。在真实项目下不会只采用一个编程语言，在不同场景下采取不同的编程语言即可，对于做硬件的人知道ASIC和FPGA，在高频量化交易场景下通常不会只使用一种处理器，以在交易标准和规则时刻变化的场景下满足高频交易的计算要求。

目前绝大部分的AI算法开发都是依托python和pytorch框架进行开发，修改模型架构、训练、验证算法假设非常快捷方便，但是目前的CV和NLP都是计算密集型的任务，对于计算效率要求非常高。事实上，由于动态脚本语言传统的解释执行机制效率相对较低，在高性能场景下已经引入了 JIT 编译、字节码复用等优化手段。编译器技术的演进（如 LLVM）使得我们可以用 Python 编写前端，而底层自动编译为极致优化的机器码（如 Numba 或 MLIR），这正在模糊静态与动态语言的界限。

2. 动态语言 Compiler/Runtime：Python/JS/Java
